The ragged edge, and a cast that answers when asked

Where this picks up. Safari showed both dotted underlines in note 28, so the receipt is shipped: .dsp now uses text-decoration: underline dotted and every receipt on this page is drawn by production CSS. The always-visible cast list from note 28 is retired per your call — explanations appear only when a marked character is clicked individually (section 3). New question first, though: what a long URL should do when it wraps (sections 1 and 2).

1 · Where the long URL falls — alignment when it wraps

today — centred, breaks anywhere
https://www.example-shop.co.uk/products/kitchen/espresso-machines/lever-operated?colour=stainless steel&campaign=spring_newsletter_2026&utm_source=weekly digest&ref=a%26b

The problem. Four ragged edges. Every line starts somewhere new, so the eye re-finds its place four times, and a break in the middle of kitchen looks the same as a break at &.

A — left when it wraps, centred when it fits
https://www.example-shop.co.uk/products/kitchen/espresso-machines/lever-operated?colour=stainless steel&campaign=spring_newsletter_2026&utm_source=weekly digest&ref=a%26b
https://example.com/docs

One CSS rule, no JS, no threshold. width: fit-content + auto margins: text that fits one line shrinks the box to itself and the box is centred — the short URL below is under the same rule and hasn't moved. Text that wraps takes the full width and left-aligns. The layout engine is the wrap detector.

B — A + hanging indent on continuation lines
https://www.example-shop.co.uk/products/kitchen/espresso-machines/lever-operated?colour=stainless steel&campaign=spring_newsletter_2026&utm_source=weekly digest&ref=a%26b

The indent is the "no space here" signal. A tucked-in line is how every code editor says "this is still the previous line" — a continuation, not a new item. First line flush, the rest 1.5ch in. (Cost: on a one-liner the box carries the unused 1.5ch, so centring shifts about half a character. Invisible in practice; if it ever bothers, A alone still stands.)

C — A + B + breaks prefer the structure
https://www.example-shop.co.uk/products/kitchen/espresso-machines/lever-operated?colour=stainless steel&campaign=spring_newsletter_2026&utm_source=weekly digest&ref=a%26b

Lines end where the URL has joints. A <wbr> after each delimiter lets lines end on / ? & = — characters that visibly cannot end a URL, so the break explains itself. overflow-wrap: anywhere stays underneath as insurance: one segment longer than the whole line still breaks mid-word rather than overflowing. Server-side, url_line_parts emits the <wbr>s; they are unselectable and never reach the clipboard.

Recommendation: C (which contains A and B). All three are pure CSS plus invisible <wbr> tags — no JS, so the no-JS page gets the same layout. Resize this window and the breaks re-place themselves; the short URL never leaves centre.

2 · Saying "no space here" at the break, explicitly

simulated — gutter arrow on continuation lines
https://www.example-shop.co.uk/products/kitchen/espresso-machines/lever-operated?colour=stainless steel&campaign=spring_newsletter_2026&utm_source=weekly digest&ref=a%26b

Simulated — these line breaks are hand-placed so you can judge the look; the browser did not choose them. A real version needs JS measuring line boxes and re-running on every resize.

Recommendation: don't. Three reasons to leave the explicit marker unmade:
  • The hero's whole promise is that what you see is what the URL contains. The arrow is a character the URL does not contain, added to the one line whose job is to add nothing. (Same reason CSS hyphens is out — a hyphen at the break reads as part of the address.)
  • It needs JS, so the no-JS page loses the signal — while B and C above give it for free, to everyone.
  • The receipt already guarantees the other half: a real space always wears the dotted underline, so a bare, unmarked break can never be hiding a space. Indent + delimiter-breaks say "continues"; the receipt says "and a space would have been visible".

Live — click the dotted space, the red escape, or the grey %26. The explanation is one cast entry from note 28, floated at the finger; nothing exists until asked, and Esc or a click elsewhere dismisses it. The invisible characters are thin targets, so the clickable area is padded a few px beyond the mark. Concerns: it floats over the card (edge collisions need care on phones), and it needs JS — no-JS gets a title tooltip as the crumb, plus the record in the fold as always.

Live — same clicks, calmer answer. Clicking a marked character (hero or slice row) opens the fold if it's closed and one cast line appears above the record, pulsing once. Nothing floats, nothing can collide with an edge, and the entry sits next to the record it explains. Cost: the eye travels from the clicked character down to the fold — the answer is not at the finger.

Mild recommendation: A — it is the literal shape of "explain this one when I click it", and the tie between character and explanation is strongest at zero distance. B is the safe fallback if A feels floaty on the phone. Shared either way:
  • Only marked characters answer (receipt spaces, red hidden characters, kept escapes) — plain text stays inert.
  • One answer at a time; asking another swaps it.
  • Production: the server wraps each marked run in a real <button> (focusable, aria-expanded) with a title as the no-JS crumb; the behaviour lives in preview.js keyed on html.js.
  • The always-visible cast list is dead; note 28's entry dress survives as the answer's body.
