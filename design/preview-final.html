YuioLink · design note 14 · final

Informative and exact, at the same time

The lid, properly diagnosed. It was not the drained styling and not the transition — it was the stacking. When a <details> is open, current browsers render its contents inside a ::details-content box. That box is the grid item, not my <a>, so .pv-cover > * never matched it, it auto-placed into row 2, and the button sat one lid-height below. Variant A only looked correct because display: none emptied row 1.

The fix is to stop stacking: no grid at all, lid removed from flow when open. The button is then the only thing in the container and lands exactly where the lid was, in every browser, with no dependency on a young pseudo-element. That also settles the motion question — there is nothing left to animate.

1 · Phone metadata: source and licence

Crate: phonenumber 0.4.0+9.0.33 — a Rust port of Google's libphonenumber, maintained under the Whisperfish project (the Signal client for Sailfish), tracking libphonenumber 9.0.33. It parses the upstream metadata XML in a build script and serialises it with postcard, so there is no runtime XML and no network fetch.

Licence: Apache-2.0 (the crate), and the bundled metadata is Apache-2.0 from Google. YuioLink is dual MIT / Apache-2.0, so the Apache side already covers it — but a distributed binary must carry the attribution. Concretely: add the crate and libphonenumber to NOTICE, which this repo already has, and keep LICENSE-APACHE as is. Your own code stays dual-licensed; only the combined binary picks up the obligation.

What it actually buys — and it is not the grouping. The tables give PhoneNumberType, which distinguishes PremiumRate, TollFree, Mobile and FixedLine, plus the region. Premium-rate detection is the one real hazard a tel: link carries, and nothing else in the stack can see it. That is the case for the dependency; pretty digits are a side effect.

Costs, honestly: the metadata is a few hundred kilobytes in the binary, the build script adds time, and the tables go stale — they need a dependency bump to stay current. phonenumber also pulls regex, which the server does not currently use.

The table is where informative and exact stop fighting. Repeated keys get their own rows instead of vanishing into an & chain; values are decoded for reading (udp://… rather than udp%3A%2F%2F…); and the two-word tags say which row is evidence and which is a label — the note's point, made once per row instead of as a paragraph. Underneath, "Exactly as stored" carries the raw percent-encoded string, and that is what ⌘C copies.

The address stays the headline because it is what the link is; the pre-written words go in the table, tagged for what they are. This is the first design in fourteen rounds where a subject a visitor would unknowingly send is impossible to miss.

4 · The rule the table settles

Headline = what the link is. Table = what it carries. Exact line = what is stored. Three registers, no overlap, and every character present in at least one of them.

It also resolves the argument I kept having with myself about emphasis. The headline can be formatted for reading (grouped digits, decoded values, highlighted domain) precisely because the exact line is always underneath it — nothing is being hidden, so the readable version costs nothing. Without that line, every improvement to legibility was a small lie; with it, none of them are.

Still open for whoever picks this up: whether the exact line should be collapsed behind a disclosure on long bodies (a magnet's is ~200 characters and currently the tallest thing on the card); whether http(s) pages should gain the same table for their query strings, which would unify the two layouts at the cost of changing a page that already works; and whether the region/type chips should appear for sms: too, where the same tables apply.
