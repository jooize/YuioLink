YuioLink · design note 17

Marks and wraps

Your marks generalise into one rule, and it is a good one. A key cell either shows, dim, the literal character that introduces that part in the stored string — ;sid, ?next, &theme, #step-2 — or it shows, unmarked, a name we gave a part: user, port, path, to. Marked = the URL's own characters, verbatim. Unmarked = our label. The table becomes the URL unrolled vertically; read the key column top to bottom and the delimiters appear in stored order.
  • Second path parameter? Never ,sid2 — each parameter brings its own semicolon in the URL (/reset;sid=9f2c;lang=no), so each row carries it: ;sid, then ;lang. Same for the query: one ?, then & forever — exactly as you wrote it.
  • The rule reaches the other formats for free. magnet becomes ?xt &dn &tr &tr; sms becomes ?body; mailto's cc/subject take their marks while the to rows stay unmarked — recipients are positional in the URL, so to is our word, and the rule shows that honestly.
  • No empty cells anymore. A row whose stored text has no = — ?join, #step-2 — spans the full width: the key is the whole item, so there is nothing missing to leave a hole for. That was the "loose join".
  • sms button verb: "Message +47 991 23 456", not "Text" — per review, and it also stops colliding with the site's own Text link kind.
Fragments, as they actually work. A URL has at most one fragment: the first # wins, and everything after it is a single opaque string the browser keeps for the page — the spec gives it no structure at all. But there is a strong convention of smuggling query syntax into it (OAuth's implicit flow returns #access_token=…&expires_in=…), so: if the fragment is =/&-shaped, unroll it by that convention — first row keyed #access_token, the rest &expires_in, exactly like a query — otherwise one full-width row with the literal text, #step-2. Your comma example (#step-2=blah,step-3=bleh) has no convention behind the comma, so it stays honest: key #step-2, value blah,step-3=bleh — we only ever unroll on &.

And yes to colouring unusual escapes in the URL line. Same palette as everywhere else: ordinary escapes (%3A, %20) dim to encoding noise; an escape that decodes to something invisible or direction-changing goes danger red — the same event that fires the Hidden Characters chip, so the chip and the red characters always appear together.

The convention case, unrolled by your rule: first row wears the #, the rest wear & — a fragment carrying a whole query-shaped payload, which is exactly how OAuth hands out access tokens. This is the card that justifies unrolling fragments at all: a bearer token in a shared link is worth a flat row someone will actually read. An unshaped fragment stays one full-width literal row (#step-2, first card); a comma gets no special treatment — we unroll on & and nothing else.

The rule pays off here: the two to rows are unmarked because the URL never says "to" — recipients are positional, comma-joined, and the word is ours. ?cc and &subject are the URL's own keys and wear its own punctuation. A reader who never learns the rule still gets a flat list; a reader who notices it can reconstruct the stored string's shape from the key column alone.

The headline drops word-break: break-all — that rule snapped the ID wherever the line happened to end, hence the orphaned G6. Now a <wbr> after each delimiter (:, @, /) offers the clean break points, so on a narrow screen the whole ID steps down to its own line intact; overflow-wrap still splits a token that could never fit on one line, like a magnet's 40-character hash — nothing can overflow the card. Same fix serves mail (breaking at the @, never inside a domain) and every other headline.
