Sits in the browser-toolbar band, and a fixed corner chip on a scrolling page needs position: fixed — the one variant that adds real complexity.

E2 is the one I'd take: it is the smallest change (unset position inside the mobile block), it removes the orphan problem for centred and bottom layouts, and the chip stays exactly where the eye starts the card. It also makes bottom-alignment viable, since the chip no longer strands. E3 is prettier when the kicker is short but needs a phantom spacer to keep the heading centred, and it breaks down if a name wraps.

D · WHEN THE TEXT IS LONGER THAN THE BOX

Today the box is capped at 60vh and scrolls — including without JavaScript, which is the bit to fix first: the cap has to be applied by text.js, so a no-JS visitor gets the whole snippet in flow and the page scrolls normally. Given that, the question is what the JS version does. Copy always takes the full text regardless of what is shown, so collapsing costs nothing there.

D1Collapse with a fade and a Show-all pill Capped at roughly ten lines with the last rows fading out, and a pill straddling the bottom edge that names the size. Clicking expands in place; the pill becomes Show less. Says two things at once — there is more, and how much more. My pick.

The pairing to decide: D4 (no cap) is the simplest and matches the no-JS rendering exactly, which is worth something on a page whose whole point is "read this once". D1 wins when a snippet is genuinely long — an SSH key blob, a config file — where a screen of monospace between the heading and the Copy button pushes the button off-screen. A middle road exists and is what I would ship: no cap until the text passes some threshold (say 24 lines or 60vh, whichever comes first), then D1. Short snippets behave like D4, long ones collapse.
